- (decision) PHASE 2 BLOCKER + recommended answer (coordinator, 2026-08-02). The P1 fix for review-defect #3 makes dispose() call firestore.terminate() before app.delete(). Because cloud_firestore 6.4.1 caches FirebaseFirestore in a process-lifetime static map with no eviction hook, a same-process dispose->re-resolve of the SAME account now returns that terminated instance and throws FirebaseException. Correct trade for Phase 1 (loud, deterministic failure instead of the prior silent misbehaviour; nothing reads through the registry yet) — but Phase 2 disposes and re-resolves on EVERY account switch, so A->B->A would throw. The fixer's suggested follow-ups were 'process restart on revisit' or 'an upstream cloud_firestore fix'; neither is attractive. RECOMMENDED ANSWER for Phase 2: stop disposing on switch. Make accountFirebaseProvider keepAlive rather than autoDispose so a named app is created once per account per process and torn down only on explicit account REMOVAL (or process exit). The <=5 cap already bounds this at 5 apps x 20MiB = 100MiB, which is the budget already accepted in P1-A. That sidesteps the SDK's un-evictable instance cache entirely, and makes review-defects #2/#3 unreachable in normal operation rather than merely handled. Decide this at the start of Phase 2, before the first collection cuts over.
