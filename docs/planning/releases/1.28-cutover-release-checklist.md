# 1.28 Cutover release checklist (DNI-490)

Story: Linear DNI-490 · bead `learning-tracker-fyh.32` · Epic 1 *One learning record, everywhere*.

This is the release record for the AD-49 cutover. From this release on, every learning write goes to `learning_events`. The five retired collections (`completions`, `learning_ledger`, `streak_events`, `bookmarks`, `learning_order`) stop taking client writes, and the four retired callables are removed from production. AD-13 applies: there is no data migration. The old collections are retired, not converted.

The release operator (the release agent) fills in the evidence columns. A row left as **open** blocks the production promote or store submission.

### Findings from the readiness check

The pending items below are not new retirement work. They are leftovers that other stories hand to the cutover, and `--enforce` cannot go green until they are gone.

- **(a) R15 `c0Stub`.** The C0 contract (DNI-524) gives the deletion of `lib/domain/learner_state/c0_stub.dart` to DNI-490. Its call-site inventory is already empty, so removing it changes no behaviour.
- **(b) R16 `purged_at` in `firestore.rules`.** The only hits are the update whitelists inside the `completions` and `learning_ledger` match blocks. They disappear when T2 reduces those blocks to deny-all writes. The R16 note in `R16.json` names this hand-off.
- **(c) R16 legacy tutor-grant keys (DNI-487).** `can_edit_goals`, `can_edit_stages`, `can_edit_study_days`, `can_reset_completion` and `can_bulk_prior_completion` were still named in `functions/src/tutor_invites.ts`, which strips them from a grant on the parent's next update, and in a lib constant that only tests read. DNI-487 left them pending until DNI-488 landed, and DNI-488 has landed. The cutover keeps the behaviour and drops the names. `updateTutorGrantPermissions` now strips every permission key outside the AD-53 set, and the list of names moves to the tests. This is the smallest change that lets `--enforce` pass. It is recorded as a deviation from "adds no further retirement work".

## 3. Backend release before the app (AC-3, AC-6; T4)

`.github/workflows/deploy-play-store.yml`:

1. `gate-ci-status` passes only when ci.yml is green for the release SHA. That includes rules, functions, the dry-run `backend-deploy-gate`, and the release-script tests.
2. `backend-deploy` (needs `gate-ci-status` and the AD-54 `perf-gate` (§4), blocking, not conditional, one run at a time) runs `node tool/firebase_backend_release.mjs --mode deploy --project torah-study-tracker`:
   - `firebase functions:list --json`. A failed or unreadable list fails the job.
   - `firebase functions:delete tutorResetCompletion tutorBulkPriorCompletions deleteBulkMarkedCompletions tutorUpsertBookmark --force`, whenever any of the four is still deployed.
   - `firebase functions:list --json` again. The job fails if any of the four remains or the list cannot be read.
   - `firebase deploy --only firestore:rules,firestore:indexes,functions`, once, never retried.
3. `deploy` (the app release) needs `backend-deploy`. A missing `FIREBASE_TOKEN`, or a failure in the list, delete, verification or deploy step, stops the app release.

Since fyh.324, a red, cancelled or skipped `perf-gate` stops `backend-deploy` as well as `deploy`. Neither job has a job-level `if:`, so each runs only when every job it needs has succeeded. The production backend cutover therefore never ships without the matching app. `validateReleaseWorkflow()` enforces this wiring.

Evidence in this story: `node --test tool/firebase_backend_release.test.mjs` simulates every failure path and checks the real workflow wiring. CI runs it in the `backend-deploy-gate` job, together with `--mode dry-run`.

[ASSUMPTION] The deploy does not pass `--force`. If production still hosts any other function that is absent from source, the non-interactive deploy stops, and the release fails closed for the operator to decide.

## 4. Engine perf gate (AC-5; T5)

`learning_tracker/test/benchmark/learner_state_engine_benchmark_test.dart` (tagged `perf`):

- **Workload:** 20 learners × (40,000 leaf events + 200 node events) on the largest bundled corpus, chosen by leaf count. Today that is `arukh_hashulchan`, with 25,097 leaves. The shape is the cutover shape: main track only, a deadline goal, chazara repeats, one void in every 100 learns, and before-tracking node events.
- **Gate:** for each learner, the warm engine recompute plus `dailyTarget` must be under `kRecomputeBudget` (1 s, `test/benchmark/perf_budget.dart`).
- **Recorded, not gated:** the cold first load, which decodes the stored log through the AD-52 codec and then runs the engine once. Both numbers go into `build/perf/learner_state_engine_benchmark.json`. `test/benchmark/engine_benchmark_record_test.dart` (main lane) proves that a slow cold load never fails the gate.
- **CI:** non-blocking in ci.yml's `perf` job (ruling B12). In deploy-play-store.yml it is the **blocking** `perf-gate` job. Both `backend-deploy` and the app `deploy` job need it (fyh.324). That job uploads the run record as `cutover-perf-record-<ref>`.

Provisional run during DNI-490 (shared, loaded build host; not the reference device): worst warm 651 ms, worst cold 1,124 ms, gate passed.
