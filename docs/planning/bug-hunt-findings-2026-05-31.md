## [high/correctness] Self-paced 'per_week' pace is converted to a per-study-day rate with ceil(), inflating any weekly pace below 8 to 1/study-day (up to 7x intended) and flooding the overdue queue  (tracks)
- File: `learning_tracker/lib/features/scheduler/presentation/providers/scheduler_providers.dart:740`
- Symptom: A learner who sets a modest weekly pace (e.g. '1 per week', '2 per week', up to 7 per week) on a self-paced track sees the scheduler expect ~1 item every study day (effectively up to 7/week), so 'due today' over-schedules and overdue items pile up far faster than the chosen pace. On a back-dated/older track this produces a large spurious overdue backlog versus the true expected position.
- Root cause: The authoritative overdue/today projection computes `final pace = PaceCalculator.paceToDaily(paceValue, pacePeriod).ceil();` (scheduler_providers.dart:740). paceToDaily('per_week') divides by 7 (pace_calculator.dart:177-182), so 1..7 per week map to 0.14..1.0, and `.ceil()` rounds every one of them up to 1. selfPacedSchedule then assigns `pace` (=1) new ref PER STUDY DAY (overdue_schedule.dart:114-125), i.e. 1/study-day ≈ up to 7/week regardless of the user's weekly setting. selfPacedSchedule requires an integer >=1 pace (it throws on <=0), so sub-7 weekly paces cannot be represented at the current per-study-day granularity. derivePaceFromDeadline also returns 'per_week' values that can be 1..7 (goal_helpers.dart:138), so deadline-derived goals hit the same inflation.
- Fix: Stop collapsing a weekly pace into a per-study-day integer. Either (a) make selfPacedSchedule accept a fractional/`per_week` pace and distribute weekly units across the actual study days of each week (assign ceil over the week, not per day), or (b) compute units expected by date as `floor(paceValue/7 * elapsedCalendarDays)` / per-week accumulation rather than `ceil(perDay)` per study day. At minimum, do not `.ceil()` a sub-1 daily rate up to 1 per study day — accumulate the weekly quota across the week so '1 per week' schedules exactly one ref per 7-day window.
- Verify: Confirmed end-to-end and reachable.

CONVERSION BUG (the cited line): scheduler_providers.dart:740 computes `final pace = PaceCalculator.paceToDaily(paceValue, pacePeriod).ceil();`. paceToDaily (scheduler/domain/services/pace_calculator.dart:176-182) returns `paceValue / 7.0` for 'per_week', so weekly paces 1..7 map to 0.14..1.0, and `.ceil()` rounds all of them up to 1.

SCHEDULE INFLATION: selfPacedSchedule (scheduler/domain/projection/overdue_schedule.dart:92-128) throws on pace <= 0 (so a sub-1 daily rate cannot be represented at all) and otherwise assigns exactly `pace` (=1) refs PER STUDY DAY (the `for (var i = 0; i < pace ...)` loop, lines 115-122). So a '1 per week' goal schedules 1 ref every study day = up to 7/week (min(7, studyDaysPerWeek)/week), independent of the user's weekly setting.

NO DOWNSTREAM CORRECTION: project() (scheduler/domain/projection/overdue_projection.dart:30-60) is a pure pass-through — every uncompleted unit dated before today becomes overdue, every uncompleted unit dated today becomes dueToday, with NO pace cap. _buildProjectionTasks emits those refs directly as DailyTasks (scheduler_providers.dart:805-846), and its own doc comment calls it "the authoritative source of truth for the overdue/today buckets (architecture §4)". The only limiter is total scope length, so on a back-dated/older track the inflated rate accumulates a large spurious overdue backlog. overdueCountForCurriculum and allDailyTasksProvider consume this directly.

REACHABILITY (user can actually set sub-8 per_week): step_goal.dart defaults `_paceUnit='per_week'` (line 41); onPaceUnitChanged freely selects 'per_week' (line 300-302); the decrement handler allows `_paceValue` down to 1 (line 294); goal_cards.dart exposes both the per_week segment (line 180) and the +/- stepper. There is NO clamp forcing weekly pace >= 8. edit_track_screen.dart behaves the same. derivePaceFromDeadline (goal_helpers.dart:119-139) also returns pacePeriod:'per_week' with values that can be 1..7 when scope is small relative to study-days, so deadline-derived goals hit the same path via lines 730-736.

NOT BY-DESIGN: the SAME provider keeps the fractional double daily rate (pacePerDayMap, Map<CurriculumId,double>) at lines 903 and 935 without any ceil — only the schedule-building path collapses to an integer-per-study-day and rounds up, so this is an internal inconsistency, not an intentional rounding policy.

MAGNITUDE: '1 per week' → up to 7x over-scheduling; any N<8 per_week is inflated to min(7, studyDaysPerWeek)/week >= N. The proposed fix (accumulate the weekly quota across the 7-day window instead of ceil'ing a sub-1 daily rate to 1/study-day) is the correct direction.

## [medium/data-loss] Tombstone resurrection fails when the re-completed event has a different timestamp than the tombstoned row  (sync)
- File: `lib/core/sync/merge/drift_merge_store.dart:239`
- Symptom: A completion that was purged (tombstoned) on this device and later re-marked complete on another device (or after the purge) stays permanently dead locally: the unit shows as not-completed even though Firestore says it is complete, and re-pulling never fixes it.
- Root cause: _insertCompletionIfAbsent looks for the tombstoned row via CompletionEventDao.findTombstonedEventByNaturalKey(... eventTimestamp: eventTs) (drift_merge_store.dart:239-247), which filters on t.eventTimestamp.equals(eventTimestamp) (completion_event_dao.dart:72). But the UNIQUE natural key on completion_events is {profileId, sefariaRef, stageId, trackType, curriculumId} with NO eventTimestamp (completion_events.dart:21). A re-mark produces a NEW completed_at (T2 != the tombstoned row's T1), so the lookup with eventTimestamp=T2 returns null. Execution falls through to appendEvent → INSERT OR IGNORE (completion_event_dao.dart:26), which collides with the existing tombstoned row on the 5-column UNIQUE key and is silently IGNORED. clearTombstone is never called, so purgedAt stays set and the completion remains dead.
- Fix: Make the resurrection lookup match the same 5-column natural key the UNIQUE index uses, NOT the timestamp. Change findTombstonedEventByNaturalKey to drop the t.eventTimestamp.equals(eventTimestamp) predicate (and remove the now-unused eventTimestamp parameter / its passing at drift_merge_store.dart:246). Then when a tombstoned row is found, clear the tombstone (and optionally update its eventTimestamp to the incoming value) instead of relying on the timestamp matching.
- Verify: VERIFIED GENUINE. Full chain confirmed against code (paths differ slightly from report: DAO/table live under lib/core/database/, not lib/core/data/).

1. UNIQUE natural key has NO eventTimestamp: completion_events.dart:19-23 indexes {profileId, sefariaRef, stageId, trackType, curriculumId}.
2. The resurrection lookup WRONGLY filters on it: completion_event_dao.dart:72 adds `t.eventTimestamp.equals(eventTimestamp)`, and drift_merge_store.dart:246 passes the incoming eventTs into findTombstonedEventByNaturalKey.
3. Pull path is unconditional for completions: CompletionEventMerger.merge (completion_event_merger.dart:40) calls insertIfAbsent for every decoded row; no remoteIsNewer LWW gate guards it (that gate is only on upsert kinds, drift_merge_store.dart:159-192). So _insertCompletionIfAbsent always runs.
4. purgeHistory tombstones the row but PRESERVES its original eventTimestamp=T1 (track_dao.dart:382-390 writes only purgedAt).
5. A re-mark (on this or another device) goes through CompletionWriter.commit, which queries by the 5-col key WITHOUT timestamp (completion_writer.dart:555-563), finds the tombstone, and _resurrectTombstone sets eventTimestamp=cmd.completedAt=T2 (completion_writer.dart:461) and pushes completed_at=T2 to Firestore (_outboxPayload, completion_writer.dart:736).
6. On a device that still holds the local tombstone with T1, the pull carries T2 (codec maps completed_at→eventTimestamp, completion_event_codec.dart:49-53). findTombstonedEventByNaturalKey(eventTimestamp=T2) does not match the T1 row → returns null → falls through to appendEvent → INSERT OR IGNORE (completion_event_dao.dart:26) collides on the 5-col UNIQUE key → silently ignored → clearTombstone never called → purgedAt stays set → the completion stays permanently dead locally and re-pulling never heals it.

NOT already-defended / NOT a false positive: the existing H2 unit test (drift_merge_store_test.dart:1397-1448) only passes because it reuses the IDENTICAL timestamp on both the seeded tombstone (ts=2026-05-05, line 1400) and the arriving remote row (completed_at: ts, line 1434). The realistic case (T2 != T1, produced by _resurrectTombstone) is untested and breaks. The local re-mark path is correctly timestamp-agnostic, which makes the cross-device pull path the sole failing surface — confirming this is an oversight, not by-design.

Reachability requires a specific multi-device sequence (purge/delete-history on device A → re-mark anywhere → pull onto a device still holding the tombstone), so it is not hit on every sync, but it is a real user-reachable flow given purgeHistory is a user-invoked "delete and wipe history" action. The proposed fix (drop the eventTimestamp predicate, match the 5-col natural key, clear tombstone + update eventTimestamp to incoming value) is correct.

## [medium/data-loss] Locally-persisted points-ledger rows can be permanently lost from cloud sync (enqueue is outside the DB transaction / skipped when sink is null)  (sync)
- File: `lib/core/database/daos/points_balance_dao.dart:497`
- Symptom: Points awarded/redeemed/refunded on one device never reach Firestore and never appear on the user's other devices; the per-device balances permanently diverge with no retry that ever recovers.
- Root cause: _applyDelta / createRedemption / parentAdjust commit the balance+ledger row inside db.transaction() and only call _pushLedgerEntry AFTER the transaction returns (points_balance_dao.dart:121, 204, 432). The outbox enqueue is therefore non-transactional with the ledger write — a crash in that window leaves the ledger row durable but never enqueued. Worse, _pushLedgerEntry returns early when syncSink==null (points_balance_dao.dart:499): on a cloud-born account where the features layer wires PointsBalanceDao.syncSink slightly after the first credit, that ledger delta is silently dropped from the push path. Nothing ever re-scans the local points_ledger for un-enqueued rows (confirmed: no reconciliation pass exists), so the loss is permanent. OutboxSyncWriteFacade's own doc (outbox_sync_write_facade.dart:19-23) flags that callers needing atomicity must insert the outbox row inside their own db.transaction(); the points DAO does not.
- Fix: Enqueue the points-ledger outbox row inside the same db.transaction() that inserts the ledger row (insert into Outbox directly, as the facade doc recommends), so the local write and the push intent commit atomically. Additionally, add a startup/post-wire reconciliation that re-enqueues any points_ledger rows lacking a corresponding pushed/outbox record, to recover rows written while syncSink was null.
- Verify: CONFIRMED REAL via the non-transactional-enqueue mechanism; the syncSink-null framing is mostly a false positive but does not change the verdict.

Mechanism A — enqueue outside the DB transaction (the genuine defect):
- points_balance_dao.dart commits the balance + ledger row inside db.transaction() (parentAdjust:97-119, createRedemption:170-199, declineRedemption:245-266, _applyDelta:421-430) and only calls _pushLedgerEntry AFTER the transaction returns (lines 121, 204, 270, 432).
- _pushLedgerEntry (497-509) → OutboxSyncWriteFacade.enqueuePointsLedgerEntry (413-423) → _enqueue (257-281) → OutboxDao.insertOutboxRow. So the outbox row is inserted in a SEPARATE write after commit, not atomically with the ledger row.
- OutboxDao's own contract is explicit (outbox_dao.dart:8-22): "All write paths that queue a Firestore mutation must call insertOutboxRow inside the same DB transaction as the local write, ensuring the two either both commit or both roll back." OutboxSyncWriteFacade repeats this (lines 19-23). The points DAO violates it.
- A process kill (OS memory pressure, swipe-away, crash) in the post-commit / pre-enqueue window leaves the ledger row durable but never enqueued. Confirmed there is NO reconciliation: PointsLedgerMerger (points_ledger_merger.dart) is pull-only (insertRemoteLedgerEntryIfAbsent), and LocalDataUploadService.pushAllLocalData (local_data_upload_service.dart:53-227) re-scans completions/bookmarks/goals/streaks/learning_ledger/tracks but NOT points_ledger — so a lost row is never re-enqueued. The balance row is updated inside the same txn and never synced (re-derived from ledger), so the lost delta diverges the per-device balance permanently.

Mechanism B — syncSink==null silent drop (points_balance_dao.dart:499): largely NOT reachable for the main credit path. The sink is wired by (1) the keepAlive syncOrchestratorProvider (sync_orchestrator_providers.dart:88), which is eagerly created by SyncLifecycleObserver wrapping MaterialApp at the root of the tree (sync_lifecycle_observer.dart:29, learning_tracker_app.dart:46), and (2) outboxSyncWriteFacadeProvider (sync_providers.dart:147), which is ref.watch'd by completionRepositoryProvider (completion_providers.dart:81) — the very provider that performs creditCompletion (completion_repository_impl.dart:205). Building the credit path synchronously wires the sink before the credit runs, so the alleged "wired slightly after the first credit" window is not substantiated for own-profile credits. (There is a minor real wrinkle: outboxSyncWriteFacadeProvider nulls the sink during tutored sessions at line 126 while the keepAlive orchestrator independently holds a non-null facade — but own-profile crediting is barred/intercepted in tutored mode, so this does not cause loss.)

Net: Mechanism A is a genuine, reachable, undefended data-loss defect that directly matches the reported symptom and proposed fix.

## [medium/correctness] Sync status shows 'Synced' while an account-level (profile 0) outbox row is permanently stuck  (sync)
- File: `lib/core/sync/sync_orchestrator.dart:940`
- Symptom: The SyncStatusIndicator shows the green 'Synced' cloud-done icon even though the initial learner_profile push (or any profile-0 row) is wedged — e.g. permission-denied — so the profile never actually reaches the cloud (the SYNC-2 'cloud learner_profiles stays empty' failure the drain sweep was meant to address), yet the UI reassures the user everything is synced.
- Root cause: _doDrain drains both the active profile AND profile 0 (outbox_processor.dart:201-207), because account-level rows like the bootstrap learner_profile push are enqueued under profileId 0 before any profile is active. But _recomputeOutboxStatus only queries the active profile: depth/oldestPendingAt/stuckCount are all called with _profileId (sync_orchestrator.dart:940-945) and each DAO method is scoped to a single profile_id (outbox_dao.dart:87/102/115). Profile-0 rows are therefore invisible to the status computation, so depth==0 → it emits SyncStatus.synced (sync_orchestrator.dart:991) even when a profile-0 row is stuck/dead-lettered.
- Fix: Include profile-0 rows in the status computation when _profileId != 0: sum depth/stuck across both _profileId and 0 (and take the min oldestPendingAt), mirroring _doDrain's two-profile sweep. Then degraded/pending will correctly reflect a stuck bootstrap push instead of reporting 'Synced'.
- Verify: Verified the full chain in code; the defect is genuine and reachable.

1. Profile-0 rows are real. `OutboxSyncWriteFacade._enqueue` writes `OutboxCompanion(profileId: Value(_profileId))` (outbox_sync_write_facade.dart:263-264), and `_profileId` is set from `activeProfileIdProvider` at facade construction (sync_providers.dart:74,80). `ActiveProfileId.build()` returns 0 when no profile is selected (active_profile_provider.dart:25,28). The bootstrap `learner_profile` push goes through `ProfileRepositoryImpl.createProfile -> _syncEngine.pushLearnerProfile` (profile_repository_impl.dart:100), whose facade comes from `syncWriteFacadeProvider`/`profileRepositoryProvider` watching `activeProfileIdProvider`. During first-profile onboarding no profile is selected, so the row is enqueued with profile_id column = 0. This is exactly the documented SYNC-2 case (outbox_processor.dart:196-200).

2. A profile-0 row can be permanently stuck. On push failure (e.g. permission-denied) the row is not deleted; `markAttempted` increments attempts (outbox_processor.dart:374), and once attempts >= _maxAttempts(10) the row is dead-lettered with `continue` and never deleted (outbox_processor.dart:337-348). Permission-denied from undeployed Firestore rules is a known recurring failure mode in this project.

3. The drain sees profile 0 but the status does not. `_doDrain` sweeps both the active profile and profile 0 when profileId != 0 (outbox_processor.dart:201-207). But `_recomputeOutboxStatus` calls dao.depth/oldestPendingAt/stuckCount with ONLY `_profileId` (sync_orchestrator.dart:940-945), and each DAO method filters on a single `outbox.profileId.equals(profileId)` (outbox_dao.dart:87/102/115). No code path sums across profiles for status; these DAO status methods have no other callers.

4. Result is a false 'Synced'. After a successful pull with a non-zero active profile, the orchestrator awaits `_drainOutbox('pull')` (which attempts profile 0 and fails), then unconditionally emits SyncStatus.synced (sync_orchestrator.dart:802) and re-runs `_recomputeOutboxStatus` (806). That recompute queries only the non-zero `_profileId`, finds depth==0/stuck==0, and re-emits synced via the `_everPulledOnLaunch` branch (988-991). SyncStatusIndicator maps SyncStatusSynced to the green Icons.cloud_done 'Synced' (sync_status_indicator.dart:31) even though the bootstrap learner_profile row is wedged. The same blind spot exists on the connectivity-change (523) and post-drain (340) recompute paths. No existing defense addresses profile-0 in the status computation.

The proposed fix (sum depth/stuck across _profileId and 0, take min oldestPendingAt, mirroring _doDrain) is correct and proportionate.

Severity: medium, not high. The local write always succeeds (offline-first), so no data loss; the harm is a misleading 'Synced' indicator that masks a cloud push that never lands, and it only manifests when the profile-0 push actually fails (permission-denied). Misleading status, not corruption.

## [medium/data-loss] remoteIsNewer clobbers a newer un-pushed local edit with stale remote inside the 5s window when local has no synced_at  (sync)
- File: `lib/core/sync/merge/drift_merge_store.dart:132`
- Symptom: A local edit made within ~5s of an incoming remote write, but not yet pushed (so no local synced_at recorded), is silently overwritten by an older remote value, even though the local updated_at is newer.
- Root cause: In remoteIsNewer, when |local-remote| <= 5s, the server-timestamp tie-break only runs if BOTH remoteSyncedAt and localSyncedAt are non-null (drift_merge_store.dart:132). A fresh local edit has updated_at set but no synced_at yet (it is recorded only after a successful push). So when a stale remote arrives within the window, the localSyncedAt!=null guard fails and execution falls through to the unconditional 'return true' (prefer remote) at drift_merge_store.dart:145 — overwriting the newer local edit with the older remote. For LWW kinds whose DAO does not independently re-gate on updated_at, this loses the local edit.
- Fix: Before defaulting to 'prefer remote', when only one side has a synced_at (or neither does) within the window, fall back to comparing the client updated_at (prefer the strictly-newer updated_at; only treat true equality as the convergence tie that prefers remote). I.e. do not let a missing local synced_at downgrade a demonstrably-newer local updated_at.
- Verify: CONFIRMED REAL (narrowed scope). The fall-through is exactly as reported: drift_merge_store.dart:132 gates the synced_at tie-break on `remoteSyncedAt != null && localSyncedAt != null`; if either is null it falls through to the unconditional `return true` (prefer remote) at drift_merge_store.dart:145, ignoring which client updated_at is newer.

Reachability of a NEWER un-pushed local edit being clobbered is genuine, but only for the SharedPreferences-backed mergers (notification_settings, ui_preferences, gamification_settings). Those read currentUpdatedAt from SyncKv and, when null, fall back to a per-profile prefs timestamp (ui_preferences_merger.dart:59-69; notification_settings_merger.dart:60-72; gamification_settings_merger.dart:76-77). That prefs timestamp is written on a LOCAL edit with no push needed (notification_providers.dart:319-325), so localUpdatedAt can be the user's fresh edit time.

localSyncedAt is null precisely when this fires: SyncKv (backing both currentUpdatedAt and currentSyncedAt) is written ONLY by mergers via persistUpdatedAt — rg confirms lib/features/sync/ (push/outbox) never touches synced_at or SyncKv. So a device that edited locally but has not yet pulled+merged a remote row for that key has currentUpdatedAt=null (→ prefs fallback = local edit time) and currentSyncedAt=null simultaneously. When a stale remote (updated_at older than the local edit but within 5s) arrives, diff<=5s, the tie-break guard fails, and `return true` overwrites the newer local edit. The prefs mergers then write the value unconditionally (ui_preferences_merger.dart:85-133) and stamp updatedAtMs with the stale remote (ui_preferences_merger.dart:142-146) — no downstream re-gate, edit permanently lost.

Not by-design / not pinned: the only related test (lww_symmetric_test.dart:1078 'missing synced_at → remote wins') uses _remoteSkew=12:00:02 NEWER than _localSkew=12:00:00, validating the correct newer-remote case; the bug's strictly-older-remote-within-window-no-synced_at case is untested. Docstring rule 5 ('missing or equal → prefer remote') targets the convergence tie (test :1088), not discarding a demonstrably-newer client updated_at.

Scope caveat (why medium): the SyncKv-only LWW mergers (bookmark, learner_profile, track_config, settings, stage_definition, goal, profile_program) have no local-edit fallback — their localUpdatedAt is the last-applied REMOTE value, so the literal 'newer un-pushed local edit' framing does not apply to them. Genuine only for the 3 prefs-backed settings kinds; trigger is a narrow ~5s cross-device concurrent-edit window before the first inbound merge for that key; lost data is a recoverable preference value, not learning progress. Proposed fix (prefer strictly-newer updated_at within window when synced_at signal is absent on a side; only true equality defaults to remote) is sound and keeps all existing lww_symmetric_test cases green.
