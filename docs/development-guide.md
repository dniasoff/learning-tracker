## Prerequisites

- **Flutter SDK** 3.29.4+
- **Dart** 3.10.8+
- **Android SDK** (API 21+, i.e., Android 5.0 Lollipop minimum)
- **Git**
- **FlutterFire CLI** (for Firebase configuration generation)

## Environment Setup

### Android Studio

1. Install Android Studio with the Flutter and Dart plugins.
2. Configure the Android SDK path in Android Studio settings.
3. Create an Android emulator (API 21+ recommended) via the AVD Manager.

### VS Code

1. Install the following extensions:
   - **Dart** (Dart-Code.dart-code)
   - **Flutter** (Dart-Code.flutter)
   - **Flutter Riverpod Snippets** (robert-brunhage.flutter-riverpod-snippets)
   - **Drift DB Viewer** (for inspecting Drift-generated database schemas)
   - **Error Lens** (usernamehw.errorlens) for inline diagnostics
2. Enable "Format on Save" in VS Code settings to keep code formatted automatically.
3. Set the Dart line length to 80 in your workspace settings to match the project's formatting rules.

### Recommended Configuration

Add to `.vscode/settings.json` (not checked in):

```json
{
  "dart.lineLength": 80,
  "editor.formatOnSave": true,
  "[dart]": {
    "editor.defaultFormatter": "Dart-Code.dart-code"
  }
}
```

## Firebase Configuration

The app uses the Firebase project **torah-study-tracker**. Firebase provides authentication, Firestore for cloud sync, and remote content delivery.

### Required Files

- **Android**: Place `google-services.json` in `android/app/`. Obtain this file from the Firebase Console under Project Settings > General > Your Apps > Android app.
- **Firebase Options**: The file `lib/firebase_options.dart` is generated by FlutterFire CLI. Regenerate it if the Firebase project configuration changes:

```bash
flutterfire configure --project=torah-study-tracker
```

### Firebase Services Used

| Service | Purpose |
|---|---|
| Firebase Auth | Anonymous and email authentication |
| Cloud Firestore | Cloud sync, content delivery |
| Firebase Hosting | Firestore security rules deployment |

### Local Development

For local development without Firebase access, the app falls back to bundled content in `assets/content/hierarchy/`. Authentication can be bypassed in test builds. All database operations use the local Drift SQLite database regardless of Firebase connectivity.

## Code Generation

This project uses `build_runner` for code generation with the following generators:

- **Drift** - Database tables, DAOs, and queries
- **auto_route** - Type-safe routing and navigation
- **freezed** - Immutable data classes with unions
- **riverpod_generator** - Type-safe Riverpod providers
- **json_serializable** - JSON serialization/deserialization

Run code generation after changing any annotated files:

```bash
dart run build_runner build --delete-conflicting-outputs
```

For continuous generation during development:

```bash
dart run build_runner watch --delete-conflicting-outputs
```

Generated files use the `.g.dart` and `.freezed.dart` suffixes. Never edit these files manually.

## Testing Strategy

### Test Layers

The project maintains **531+ tests** across four layers:

1. **Unit tests** - Pure logic in services, utilities, and domain models
2. **Widget tests** - UI components with mocked dependencies
3. **Integration tests** - Cross-feature flows using in-memory databases
4. **Acceptance tests** - Story-based tests organized by epic (15 files, 401 tests)

### Test Infrastructure

- **In-memory Drift databases** for fast, isolated test execution (no disk I/O)
- **Mocktail** for mock/stub generation (not Mockito)
- **Test fixtures** in `test/fixtures/` for reusable test data factories
- **Test helpers** in `test/helpers/` for common setup utilities

### Story-Based TDD Workflow

The recommended development loop:

1. **Implement** the feature or fix.
2. **`make test-story-X.Y`** - Verify the specific story passes.
3. **`make test-epic-N`** - Verify no regressions in the epic.
4. **`make ci`** - Full validation before pushing.

### Coverage Targets

| Layer | Target |
|---|---|
| Core | >= 80% |
| Domain | >= 80% |
| Data | >= 70% |
| Presentation | >= 60% |

## Common Development Tasks

### How to add a new feature module

1. Create the feature directory under `lib/features/<feature_name>/` with the standard three-layer structure:

```
lib/features/<feature_name>/
├── data/
│   ├── repositories/
│   └── services/
├── domain/
│   ├── models/
│   ├── repositories/
│   └── services/
└── presentation/
    ├── providers/
    ├── screens/
    └── widgets/
```

2. Define domain interfaces first (repository abstract classes, domain models with `freezed`).
3. Implement the data layer (repository implementations, service integrations).
4. Build the presentation layer (providers, screens, widgets).
5. Register any new routes in `lib/core/navigation/app_router.dart`.
6. Follow the dependency rule: presentation depends on domain, data implements domain, features never import from other features.
7. Run `dart run build_runner build --delete-conflicting-outputs` to generate code for any annotated classes.

### How to add a new database table

1. Create the table class in `lib/core/database/tables/<table_name>.dart`:

```dart
import 'package:drift/drift.dart';

class MyNewTable extends Table {
  IntColumn get id => integer().autoIncrement()();
  TextColumn get name => text()();
  DateTimeColumn get createdAt => dateTime()();
}
```

2. Create the corresponding DAO in `lib/core/database/daos/<table_name>_dao.dart`:

```dart
import 'package:drift/drift.dart';
import '../app_database.dart';
import '../tables/my_new_table.dart';

part '<table_name>_dao.g.dart';

@DriftAccessor(tables: [MyNewTable])
class MyNewTableDao extends DatabaseAccessor<AppDatabase>
    with _$MyNewTableDaoMixin {
  MyNewTableDao(super.db);

  // Add query methods here
}
```

3. Register both the table and DAO in `lib/core/database/app_database.dart`:
   - Add the table to the `@DriftDatabase(tables: [...])` annotation.
   - Add the DAO to the `daos: [...]` list.
4. Run `dart run build_runner build --delete-conflicting-outputs`.
5. Increment the `schemaVersion` getter in `app_database.dart` (currently at 15).
6. Add the migration logic in the `migration` getter to handle the schema change.

### How to add a new screen

1. Create the screen widget in `lib/features/<feature>/presentation/screens/<screen_name>_screen.dart`:

```dart
import 'package:auto_route/auto_route.dart';
import 'package:flutter/material.dart';

@RoutePage()
class MyNewScreen extends StatelessWidget {
  const MyNewScreen({super.key});

  @override
  Widget build(BuildContext context) {
    return Scaffold(
      appBar: AppBar(title: const Text('My New Screen')),
      body: const Center(child: Text('Content')),
    );
  }
}
```

2. Register the route in `lib/core/navigation/app_router.dart` by adding an `AutoRoute` entry:

```dart
AutoRoute(page: MyNewRoute.page, path: 'my-new'),
```

3. Apply guards if the screen requires authentication, profile selection, or PIN verification.
4. Run `dart run build_runner build --delete-conflicting-outputs` to generate the route class.

### How to add a new Riverpod provider

1. Create the provider file in `lib/features/<feature>/presentation/providers/`:

```dart
import 'package:riverpod_annotation/riverpod_annotation.dart';

part '<provider_name>.g.dart';

@riverpod
Future<MyData> myProvider(MyProviderRef ref) async {
  // Provider logic here
}
```

2. Run `dart run build_runner build --delete-conflicting-outputs` to generate the `.g.dart` file.
3. Use the provider in widgets with `ref.watch(myProviderProvider)`.
4. For providers that return `Map<K, V>` types, see [Known Gotchas](#known-gotchas) -- you must manually author the `.g.dart` file.

## Coding Standards

### Cast-Iron Rules

These rules are non-negotiable and enforced across the codebase:

1. **Use `AsyncValue`, not custom state classes.** All async state in providers must use Riverpod's `AsyncValue<T>`.

2. **`DateTime` MUST use UTC.** All date/time values are stored and compared in UTC. Use the project's `DateUtils` for conversions.

3. **NEVER mutate state.** All models use `freezed` with `copyWith`. State updates produce new instances.

4. **Database writes MUST use transactions.** Any operation that writes to multiple tables must be wrapped in a transaction.

5. **NEVER import between features.** Features communicate only through core providers. Direct imports from one feature into another are forbidden.

6. **NEVER commit generated files.** Files ending in `.g.dart` and `.freezed.dart` are in `.gitignore` and must not be checked in.

7. **Completion records are append-only.** Completions cannot be deleted or unmarked. The `DuplicatePreventionService` guards against double-recording.

### Clean Code Principles

The codebase follows these Clean Code principles:

- **Boy Scout Rule**: Leave the code cleaner than you found it. When you touch a file, improve any small issues you encounter (naming, clarity, dead code).
- **Single Responsibility**: Each class and function has one reason to change. DAOs handle persistence, services handle business logic, providers handle state management.
- **Meaningful Names**: Variables, functions, and classes use intention-revealing names. Avoid abbreviations except well-known domain terms (DAO, DTO).
- **Small Functions**: Functions do one thing. If a function needs a comment to explain what it does, extract a well-named helper.
- **DRY (Don't Repeat Yourself)**: Extract shared logic into core services, utilities, or base classes. Never copy-paste between features.

### XP Practices

- **Simple Design**: Code passes all tests, reveals intention, contains no duplication, and uses the fewest elements possible. Do not add abstractions until a concrete need arises.
- **FIRST Tests**: Tests are Fast, Isolated, Repeatable, Self-validating, and Timely. In-memory databases and Mocktail mocks keep tests fast and isolated.
- **Continuous Refactoring**: Refactor relentlessly. The test suite provides the safety net. If a refactoring breaks tests, the refactoring is wrong.
- **Pair Programming**: Use code reviews as asynchronous pair programming. Every PR receives a review before merging.
- **Incremental Design**: Build the simplest thing that works, then evolve. The three-layer feature architecture supports incremental growth without rewrites.

## Git Workflow

1. **Branch from `dev`** - All feature branches are created from the `dev` branch.
2. **Conventional commits** - Use conventional commit format:
   - `feat: add streak tracking`
   - `fix: correct UTC date boundary`
   - `refactor: extract scheduling logic`
   - `test: add story 3.2 acceptance tests`
3. **Run `make ci` before opening a PR** - This ensures analyze, format, and all tests pass.

## Pre-Commit Hook

The project includes a pre-commit hook that automatically runs:

1. **`dart format`** - Checks formatting on staged `.dart` files.
2. **`dart analyze`** - Runs static analysis.

The commit is **automatically blocked** if either check fails. Fix the issues and re-commit.

## Known Gotchas

### Map return types require manual `.g.dart` files

Riverpod's code generator does not support providers that return `Map<K, V>` types. If you create a provider that returns a Map, the generated `.g.dart` file will be incorrect or fail to compile. You must manually author the `.g.dart` file for these providers.

### `progress_providers.g.dart` is manually authored

The file `lib/features/progress/presentation/providers/progress_providers.g.dart` is manually written because it contains providers that return Map types. Do not delete this file or attempt to regenerate it with `build_runner`. If you modify `progress_providers.dart`, update the `.g.dart` file by hand to match.

### Generated files and `.gitignore`

Most `.g.dart` and `.freezed.dart` files are excluded from version control. However, manually authored `.g.dart` files (like `progress_providers.g.dart`) must be committed. Check `.gitignore` rules before assuming a generated file is or is not tracked.

## Troubleshooting

### `build_runner` fails with conflicting outputs

This happens when generated files from a previous run conflict with the current build. Use the `--delete-conflicting-outputs` flag:

```bash
dart run build_runner build --delete-conflicting-outputs
```

If the problem persists, clean the build cache:

```bash
dart run build_runner clean
dart run build_runner build --delete-conflicting-outputs
```

### Code generation produces stale or incorrect output

If generated files seem out of date after running `build_runner`:

1. Delete the `.dart_tool/build` directory.
2. Run `flutter pub get` to refresh dependencies.
3. Re-run `dart run build_runner build --delete-conflicting-outputs`.

### Drift migration errors at runtime

If the app crashes on startup with a schema migration error:

1. Verify that `schemaVersion` in `app_database.dart` matches the latest migration step.
2. Check that every schema version increment has a corresponding migration block in the `migration` getter.
3. For development, you can delete the app data on the emulator/device and reinstall to start with a fresh database. This is not a fix -- it confirms the migration is the issue.

### `auto_route` generation fails

If `build_runner` cannot generate route classes:

1. Verify that all screen widgets have the `@RoutePage()` annotation.
2. Check that the screen class name ends with `Screen` (the generator expects this convention).
3. Ensure the screen file is importable from the router file (no circular dependencies).

### Analyzer reports errors in generated files

Generated files sometimes produce analyzer warnings after a partial `build_runner` run. Always run a full build before trusting analyzer output:

```bash
dart run build_runner build --delete-conflicting-outputs
dart analyze
```

### Tests fail with "database is closed" errors

This indicates that a test is reusing a database instance after it has been disposed. Each test should create its own in-memory database instance. Use the test helpers in `test/helpers/` to create fresh database instances.

### `flutter pub get` fails with dependency conflicts

Run `flutter pub upgrade` to resolve transitive dependency conflicts. If that fails, check `pubspec.yaml` for overly strict version constraints.
