# Story 15.13 — Cloud Content Storage & Multilingual Fetch (DNI-121)

## Story Overview

The app currently bundles Torah learning content (Mishnayos, Bavli, Yerushalmi, Chumash, Mishna Berurah) as JSON files in `assets/content/`, totaling ~13 MB of uncompressed JSON. These are generated by `tool/seed_content.dart` (which calls the Sefaria API), committed to git, and loaded at runtime by `ContentRepositoryImpl` via Flutter's `rootBundle.loadString()`. Text content (Hebrew/English) is separately fetched via `tool/seed_text_content.dart` and hosted on GitHub Releases as gzipped JSON, downloaded on-demand by `TextDownloadService`.

This story migrates **hierarchy content** (the structure JSON currently bundled) to Firebase Cloud Storage, adds a CLI upload script that fetches from Sefaria and uploads per-language blobs, and introduces multilingual support (Hebrew, English, French, Spanish). The result is:

- Smaller app binary (~13 MB removed)
- Content updates without app releases
- Git repo no longer bloated with large JSON files
- Multilingual content support (he, en, fr, es)

**Important distinction**: This story handles the **hierarchy/structure** JSON (what is currently in `assets/content/*.json`). The **text content** pipeline (`TextDownloadService`, `TextContentConfig`, GitHub Releases hosting) is a separate concern and remains unchanged by this story, though the upload script will also generate multilingual text blobs for a future story.

## Architecture & Design Notes

### Cloud Storage Path Convention

```
gs://{storageBucket}/content/
  mishnayos/
    he.json.gz          # Hebrew hierarchy (always primary)
    en.json.gz          # English hierarchy
    fr.json.gz          # French hierarchy
    es.json.gz          # Spanish hierarchy
  bavli/
    he.json.gz
    en.json.gz
    ...
  yerushalmi/
    ...
  chumash/
    ...
  mishna_berurah/
    ...
```

### Firestore Version Schema

Collection: `content_versions`
Document ID: `{curriculum_storageKey}` (e.g., `mishnayos`, `bavli`)

```json
{
  "version": "hierarchy-v2.0",
  "updatedAt": "2026-03-17T12:00:00Z",
  "contentHash": "sha256:abc123...",
  "languages": ["he", "en", "fr", "es"],
  "itemCounts": {
    "he": 4192,
    "en": 4192,
    "fr": 4192,
    "es": 4192
  }
}
```

### Fetch Flow

```
User selects curriculum (onboarding or Settings)
  |
  v
ContentFetchService.fetchCurriculum(curriculumId, languages: [he, userLang])
  |
  +---> Check local content_download_statuses table
  |       |
  |       +---> If version matches Firestore → return cached (no fetch)
  |       +---> If no local data or version mismatch → proceed to fetch
  |
  +---> Download he.json.gz from Cloud Storage
  |       |
  |       +---> Decompress, parse, batch-insert into content_items table
  |       +---> Emit progress: downloading → parsing → storing → complete
  |
  +---> Download {userLang}.json.gz from Cloud Storage (if userLang != 'he')
  |       |
  |       +---> Merge translation fields into existing content_items rows
  |
  +---> Update content_download_statuses with new version
  |
  +---> Return success
```

### Launch Version Check Flow

```
App startup (after auth)
  |
  v
ContentVersionChecker.checkForUpdates()
  |
  +---> For each active curriculum:
  |       |
  |       +---> Read local content_download_statuses.version
  |       +---> Read Firestore content_versions/{id}.version
  |       +---> If mismatch → add to stale list
  |
  +---> If stale list non-empty:
          |
          +---> Show "Content updates available" banner/dialog
          +---> User can tap to update (re-fetch) or dismiss
```

### Integration with Existing Pipeline

The current import pipeline works as follows:

1. `OnboardingScreen` → user selects curricula → calls `CurriculumImportService.importAll()`
2. `CurriculumImportService._importOne()` → calls `ContentRepository.getContentForCurriculum()` (loads from `rootBundle`) → calls `CurriculumActivationService.activate()`
3. `ContentRepositoryImpl` loads JSON from `assets/content/{filename}.json` via `rootBundle.loadString()`, parses into `ContentItem` list, caches in memory

**After this story:**

1. `OnboardingScreen` → user selects curricula → calls `CurriculumImportService.importAll()` (unchanged interface)
2. `CurriculumImportService._importOne()` → calls `ContentFetchService.ensureContentAvailable()` (NEW — downloads from Cloud Storage if needed) → calls `ContentRepository.getContentForCurriculum()` (now reads from Drift DB) → calls `CurriculumActivationService.activate()`
3. `ContentRepositoryImpl` queries `content_items` Drift table instead of `rootBundle`

The key insight is that `CurriculumImportService` remains the orchestrator, but gains a new dependency on `ContentFetchService` which handles the cloud download. `ContentRepository` changes its data source from assets to Drift DB.

## Upload Script Design

### File: `tool/upload_cloud_content.dart`

```
Usage:
  dart run tool/upload_cloud_content.dart [options]

Options:
  --curriculum <id>     Single curriculum (default: all)
  --language <code>     Single language (default: all)
  --dry-run             Print what would be uploaded without uploading
  --force               Upload even if hash matches
```

### Structure

```dart
// tool/upload_cloud_content.dart
//
// 1. Initialize Firebase Admin SDK (uses GOOGLE_APPLICATION_CREDENTIALS env var)
// 2. For each curriculum × language:
//    a. Fetch hierarchy from Sefaria API using existing fetchers (MishnaFetcher, etc.)
//    b. For non-Hebrew languages, re-fetch with ?lang= parameter or use Sefaria translations API
//    c. Structure as JSON blob (same schema as current assets/content/*.json)
//    d. Gzip compress
//    e. Compute SHA-256 hash
//    f. Compare with Firestore content_versions doc — skip if hash matches
//    g. Upload to Cloud Storage: content/{curriculum_id}/{lang}.json.gz
//    h. Update Firestore content_versions doc
```

### Sefaria API & Language Handling

The existing `SefariaFetcherBase` and curriculum-specific fetchers (`MishnaFetcher`, `BavliFetcher`, etc.) fetch the **shape** of each curriculum (hierarchy structure) from `/api/shape/{category}`. The shape API returns English and Hebrew display names. For the hierarchy JSON, the relevant multilingual fields are:

- `displayNameHe` — always Hebrew (from Sefaria `heTitle` field)
- `displayNameEn` — currently English (from Sefaria `title` field)

For French/Spanish, the fetchers need to:
1. Use the Sefaria `/api/v3/texts/{ref}?version=all` endpoint to get available translations
2. Fall back to English display names if French/Spanish translations are unavailable on Sefaria (which is likely for most content — Sefaria primarily has Hebrew and English)
3. For UI labels (hierarchy level names like "Seder", "Masechta"), use a static translation map since these are not from the API

Practically, the hierarchy JSON per language will differ only in `displayNameEn` (replaced with the target language translation where available). `displayNameHe` remains Hebrew in all files since it is the primary liturgical text.

### Firebase Admin SDK Setup

The upload script runs as a Dart CLI tool. Since `firebase_admin_interop` (Dart Firebase Admin) has limited support, the recommended approach is:

**Option A (Recommended)**: Node.js companion script for the upload step
- Dart script generates the JSON files locally (leveraging existing fetchers)
- Node.js script uploads to Cloud Storage and writes Firestore metadata
- Keeps Sefaria API logic in Dart, Firebase Admin logic in Node.js where it is well-supported

**Option B**: Use `googleapis` Dart package directly
- `package:googleapis/storage/v1.dart` for Cloud Storage uploads
- `package:googleapis/firestore/v1.dart` for Firestore writes
- Authenticate via service account JSON (GOOGLE_APPLICATION_CREDENTIALS)
- More complex but keeps everything in Dart

The script structure:

```
tool/
  upload_cloud_content.dart         # Dart: orchestrator + Sefaria fetch
  lib/
    cloud_uploader.dart             # Dart: googleapis-based upload
    sefaria/                        # (existing fetchers — reused)
  upload_cloud_content.js           # (Alternative: Node.js upload companion)
```

## Dev Notes

### Firebase Cloud Storage Pricing

- Storage: $0.026/GB/month
- Downloads: $0.12/GB
- Current content: ~13 MB uncompressed, ~2-3 MB gzipped per curriculum across all languages
- Total stored: ~15 MB (5 curricula x 4 languages x ~750 KB gzipped) — negligible storage cost
- Per-user download: ~1-3 MB (1-2 languages x 1-5 curricula) — negligible bandwidth cost
- Free tier: 5 GB storage, 1 GB/day downloads — more than sufficient for initial scale

### Offline Behavior

- If content is already cached in local Drift DB, app works fully offline
- Cloud Storage download requires internet — show clear error with retry button
- Version check on launch fails silently when offline (local content continues to work)
- `ContentFetchService` should set a reasonable timeout (30s) and retry once on failure

### Migration from Bundled to Cloud

For users upgrading from the current bundled version:
1. On app update, the `content_items` table will be empty (new table)
2. Migration v10 creates the table but does not populate it
3. First time user opens any content-dependent screen, `ContentFetchService.isContentAvailable()` returns false
4. Trigger automatic download for all active curricula
5. Alternatively: during migration, seed `content_items` from the still-present bundled assets (one-time), so existing users have zero downtime. This is the safer approach.

**Recommended migration strategy**:
- Schema migration v10: create new tables
- Post-migration data seed: check if `content_items` is empty AND bundled assets exist → load from assets as before (one-time seed) → mark as downloaded with version "bundled-v1.0"
- On next version check, Firestore version will be newer → prompt update from Cloud Storage

### Sefaria API Rate Limits

- Sefaria API is generally permissive but has undocumented rate limits
- The existing `seed_text_content.dart` already handles 429 responses with retry
- For the upload script, the hierarchy fetching uses `/api/shape/{category}` which is a lightweight call (one call per curriculum, returns full hierarchy)
- Multilingual display names may require additional API calls if translations are needed
- Apply same pattern: 5 concurrent requests max, 200ms delay between batches, retry on 429

### Sefaria Multilingual Coverage

Sefaria primarily has Hebrew and English content. French and Spanish translations exist for some texts (notably Tanach/Chumash) but not all. The upload script should:
- Attempt to fetch French/Spanish translations
- Fall back to English display names where translations are unavailable
- Log which items lack translations for each language
- The `displayNameHe` field is always Hebrew regardless of language file

### Content Items Table vs. In-Memory Cache

The current `ContentRepositoryImpl` uses an in-memory cache (`_contentCache`). Moving to Drift DB means:
- First query will be slower (disk I/O vs. memory)
- But no need to load entire curriculum into memory at once
- Drift queries can filter/search at the SQL level (more efficient for large curricula like Mishna Berurah with 6,751 items)
- Optional: keep a small LRU memory cache on top of Drift for hot paths

### `firebase_storage` Package

The `firebase_storage` package for Flutter provides:
- `FirebaseStorage.instance.ref('content/mishnayos/en.json.gz').getData(maxSize)` for download
- Progress via `task.snapshotEvents`
- Automatic retry and resume support
